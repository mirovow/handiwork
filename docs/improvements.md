# План доработок CrossStitchApp

Документ фиксирует технические и продуктовые доработки, которые стоит сделать перед развитием проекта. Приоритеты указаны с точки зрения надежности, поддержки и готовности приложения к реальному использованию.

## P0: Базовая надежность

1. Вынести конфигурацию в переменные окружения.
   - Backend: MongoDB connection string, порт, путь к uploads.
   - Frontend: URL API вместо `http://localhost:3000`.
   - Добавить `.env.example` для backend и frontend.

2. Добавить валидацию API на backend.
   - Проверять наличие файла в `POST /patterns`.
   - Проверять MIME type и размер изображения.
   - Валидировать `width` и `height`: числа, разумный диапазон, отсутствие `NaN`.
   - Возвращать понятные HTTP-ошибки вместо неявных падений.

3. Стабилизировать работу с uploads.
   - Гарантировать создание директории загрузок.
   - Согласовать путь сохранения файлов и путь раздачи статики.
   - Продумать очистку временных/старых файлов.

4. Покрыть критические backend use cases тестами.
   - Генерация схемы при валидных настройках.
   - Ошибки при невалидных размерах/файлах.
   - Сохранение и получение прогресса.
   - Получение списка и одной схемы.

## P1: Пользовательский опыт

1. Улучшить обработку ошибок на frontend.
   - Показывать пользователю причину ошибки API.
   - Обрабатывать недоступный backend.
   - Не считать успешным ответ без проверки `res.ok`.

2. Добавить состояния загрузки и пустых данных во всех ключевых местах.
   - Главная форма генерации.
   - Галерея.
   - Workspace.

3. Улучшить autosave прогресса.
   - Показывать состояние ошибки сохранения.
   - Повторять сохранение после временной ошибки.
   - Сохранять прогресс перед уходом со страницы, если есть несохраненные изменения.

4. Уточнить продуктовую формулировку "в реальном времени".
   - Если достаточно autosave через HTTP, обновить описание.
   - Если нужен настоящий realtime между устройствами, добавить WebSocket/SSE как отдельную задачу.

## P2: Производительность и масштабирование

1. Оптимизировать workspace для больших схем.
   - Сейчас размер до 500x500 может создать до 250 000 DOM-клеток.
   - Рассмотреть canvas/WebGL или виртуализацию сетки.
   - Добавить ограничения размеров до появления оптимизированного рендера.

2. Оптимизировать хранение `patternData`.
   - Сейчас схема хранится как двумерный массив строк.
   - Рассмотреть хранение индексов палитры вместо DMC-имен в каждой клетке.
   - Проверить размер документов MongoDB на больших схемах.

3. Улучшить генерацию превью.
   - Хранить отдельное легкое preview для галереи.
   - Не загружать тяжелые данные схемы в списке, если они не нужны.

## P3: Архитектура и поддерживаемость

1. Укрепить Clean Architecture boundaries.
   - Оставлять бизнес-правила в use cases/domain.
   - DTO, HTTP, multer и Mongoose держать в infrastructure.
   - Не протаскивать детали Express/Mongoose в application/domain.

2. Добавить явные DTO и типы API.
   - DTO для создания схемы и сохранения прогресса.
   - Общие frontend-типы для `Pattern`, `Progress`, `DmcColor`.
   - По возможности синхронизировать контракт между backend и frontend.

3. Навести порядок в тестовой стратегии frontend.
   - Минимум: `svelte-check` в CI.
   - Затем unit/component tests для критичных функций UI.
   - Позже e2e-тест на поток: загрузка изображения -> workspace -> отметка прогресса.

4. Подготовить проект к CI.
   - Backend: `npm run lint`, `npm test`, `npm run build`.
   - Frontend: `npm run check`, `npm run build`.
   - Отдельно учесть MongoDB для backend/e2e тестов.

## Открытые вопросы

1. Нужна ли авторизация и привязка схем к пользователям?
2. Должна ли галерея быть общей или персональной?
3. Нужно ли хранить оригинальные изображения постоянно?
4. Какая максимальная схема считается приемлемой по UX: 100x100, 200x200, 500x500?
5. Требуется ли синхронизация прогресса между устройствами в реальном времени?
6. Планируется ли деплой на один сервер или frontend/backend будут размещаться отдельно?

## Рекомендуемый первый инкремент

Начать с P0: конфигурация окружения, backend-валидация и тесты use cases. Это даст надежную основу для следующих изменений и снизит риск скрытых ошибок при работе с файлами, MongoDB и пользовательским вводом.
