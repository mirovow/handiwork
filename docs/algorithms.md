# Алгоритмы проекта

Краткий ориентир для агентов, которым нужно быстро понять, как приложение превращает изображение в схему и как схема отображается в workspace.

## Основные точки входа

1. Backend image pipeline: `backend/src/infrastructure/services/sharp-image-processing.service.ts`.
2. Pattern use case: `backend/src/application/use-cases/generate-pattern.use-case.ts`.
3. Pattern domain model: `backend/src/domain/entities/pattern.entity.ts`.
4. Pattern API: `backend/src/infrastructure/controllers/pattern.controller.ts`.
5. Frontend create form: `frontend/src/routes/+page.svelte`.
6. Workspace renderer: `frontend/src/routes/workspace/[id]/+page.svelte`.

## Генерация размера схемы

Пользователь задает максимальную рамку схемы, например `100 x 100`.

Backend не растягивает изображение в эту рамку и не добавляет поля. Вместо этого он сохраняет aspect ratio исходного изображения:

1. Читает metadata исходника через Sharp.
2. Считает соотношение сторон исходника.
3. Оставляет одну сторону равной пользовательскому максимуму.
4. Вторую сторону уменьшает так, чтобы сохранить пропорции.

Пример:

1. Исходник `200 x 100`.
2. Пользователь задал `100 x 100`.
3. Итоговая схема будет `100 x 50`.

Фактические размеры сохраняются в `Pattern.settings.width` и `Pattern.settings.height`.

## Вырезание фона

В форме есть опция `Вышивать фон`.

Если `stitchBackground=true`, фон не вырезается: каждый непрозрачный пиксель участвует в схеме.

Если `stitchBackground=false`, используется edge-connected background removal:

1. Изображение уже приведено к итоговому размеру схемы.
2. Backend смотрит пиксели по краям изображения.
3. Краевые цвета группируются в грубые RGB buckets.
4. Выбирается доминирующий краевой цвет как цвет фона.
5. От всех краевых пикселей запускается flood fill.
6. В фон попадают только пиксели, которые:
   - связаны с краем;
   - похожи на доминирующий цвет фона;
   - не прозрачные.

Порог похожести сейчас:

```ts
dr * dr + dg * dg + db * db <= 45 * 45
```

Важно: алгоритм не удаляет весь белый цвет в картинке. Он удаляет только область, связную с краем. Поэтому белая деталь внутри объекта, например блик в глазу, должна остаться.

Ограничения:

1. Если объект касается края и похож на фон, часть объекта может быть удалена.
2. Сложный, шумный или градиентный фон может удалиться не полностью.
3. Алгоритм рассчитан прежде всего на клипарты и изображения с простым внешним фоном.

## Подбор цветов ниток

Приложение использует реальные палитры ниток, сейчас DMC и Anchor.

Для каждого непрозрачного и не удаленного пикселя:

1. Берется RGB пикселя.
2. В выбранной палитре ищется ближайший цвет.
3. Расстояние считается в RGB-пространстве:

```ts
dr * dr + dg * dg + db * db
```

Это простая евклидова метрика без perceptual color model. Она быстрая, но не всегда идеально совпадает с человеческим восприятием цвета.

## Ограничение количества цветов

После первичного маппинга в палитру:

1. Backend считает частоту каждого найденного thread code.
2. Сортирует цвета по частоте.
3. Оставляет `maxColors` самых частых цветов.
4. Пиксели, которые ссылались на отброшенные цвета, перемапливаются на ближайший цвет из ограниченной палитры.

Итоговая `pattern.palette` содержит только цвета, реально использованные в схеме.

## Модель схемы

Новые схемы имеют `schemaVersion: 2`.

`patternData` хранит не строки цветов, а ячейки:

```ts
type PatternCell = {
  x: number;
  y: number;
  stitches: CellStitch[];
};
```

Пустая клетка:

```ts
{ x, y, stitches: [] }
```

Непустая клетка сейчас содержит один основной стежок:

```ts
{
  id: `${x}:${y}:full`,
  kind: 'full_cross',
  threadCode
}
```

Модель уже допускает несколько стежков в одной клетке, но текущий генератор создает один стежок на клетку.

## Типы стежков

Поддерживаемые клеточные типы:

1. `full_cross` — полный крестик.
2. `half_cross` — одна диагональ.
3. `quarter_cross` — короткий стежок от угла к центру.
4. `three_quarter_cross` — диагональ плюс короткий стежок.

Пользователь выбирает доступные типы в форме создания схемы. Нельзя создать схему без выбранного типа. По умолчанию выбран `full_cross`.

## Выбор типа стежка при генерации

Если выбран один тип, все непустые клетки получают этот тип.

Если выбрано несколько типов:

1. Backend смотрит соседей клетки сверху, справа, снизу и слева.
2. Если сосед отличается по thread code или отсутствует, эта сторона считается boundary.
3. Если boundary образует угол и выбран `three_quarter_cross`, используется `three_quarter_cross`.
4. Иначе если boundary образует угол и выбран `quarter_cross`, используется `quarter_cross`.
5. Иначе если есть любая boundary-сторона и выбран `half_cross`, используется `half_cross`.
6. Иначе используется `full_cross`, если он выбран.
7. Если `full_cross` не выбран, используется первый выбранный тип.

Это эвристика для видимых обозначений и грубого сглаживания границ. Это не полноценный алгоритм художественного построения fractional stitches.

## Направления и углы стежков

Для `half_cross` и `three_quarter_cross` задается `direction`:

1. `slash`.
2. `backslash`.

Сейчас направление выбирается детерминированно по parity координат:

```ts
(x + y) % 2 === 0 ? 'slash' : 'backslash'
```

Для `quarter_cross` и `three_quarter_cross` задается `corner`:

1. `top_left`.
2. `top_right`.
3. `bottom_left`.
4. `bottom_right`.

Угол выбирается по boundary-сторонам клетки. Если подходящей boundary-комбинации нет, используется fallback по parity координат.

## Preview PNG

Backend генерирует preview PNG из итоговой схемы:

1. Для каждой клетки берется первый стежок.
2. Если стежка нет, пиксель preview становится белым.
3. Если стежок есть, пиксель получает RGB цвета нитки.

Preview не рисует символы стежков. Это цветовая миниатюра схемы.

## Прогресс вышивания

Progress хранится по `stitchId`, а не по координатам клетки:

```ts
completedStitches: Array<{
  stitchId: string;
  completedAt?: string;
}>
```

Причина: в будущем одна клетка может содержать несколько стежков, а backstitch/french knot вообще не являются обычными клетками.

На frontend progress хранится как `Set<string>` для быстрого lookup.

## Canvas renderer

Workspace использует `<canvas>`, а не DOM-сетку.

Renderer делает:

1. Рисует фон схемы.
2. Рисует цветные клетки.
3. Рисует символ стежка.
4. Рисует completed marker по центру клетки.
5. Рисует grid.
6. Рисует hover outline.

Клики переводятся из screen coordinates в grid coordinates с учетом `offsetX`, `offsetY` и `viewScale`.

## Оптимизации canvas

Текущие оптимизации:

1. Redraw идет через `requestAnimationFrame`.
2. Canvas backing store пересоздается только при изменении размера canvas или DPR.
3. Для pan/zoom считается видимый диапазон клеток.
4. Grid, completed markers и fallback-отрисовка клеток рисуются только в видимой области.
5. Статическая схема кэшируется в отдельный canvas layer, если размер слоя не превышает лимит.
6. Progress и hover рисуются отдельно поверх статического слоя.

Лимит статического слоя нужен, чтобы не создать слишком большой canvas и не съесть память на больших схемах.

## Известные ограничения

1. RGB distance простая и не perceptual.
2. Fractional stitch heuristic грубая.
3. Background removal хорошо работает на простом внешнем фоне, но не является полноценной сегментацией.
4. Preview PNG не отражает типы стежков.
5. Canvas renderer быстрее DOM-сетки, но для очень больших схем может потребоваться tile-based renderer, WebGL или WebGPU.
